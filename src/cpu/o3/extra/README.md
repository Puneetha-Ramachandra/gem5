# gem5-micro: MicroCPU Infrastructure

**gem5-micro** is a specialized extension of the gem5 O3 CPU designed for direct micro-op injection, trace dumping, and bypass-fetch architectural analysis. It enables high-fidelity stress testing of the O3 backend (LSQ, ROB, IQ) without requiring a full functional frontend or complex binary generation.

## Core Components

The infrastructure consists of several key files in `src/cpu/o3/extra/`:

- **`micro_insts.hh`**: A library of synthetic RISC-V micro-op primitives (`MuAdd`, `MuSub`, `MuMul`, `MuDiv`, `MuLd`, `MuSt`). These implement the `MicroStaticInstBase` for standardized serialization.
- **`MicroCPU.py`**: The Python SimObject definition. It inherits from `RiscvO3CPU` and exports the injection API to Python.
- **`micro_cpu.hh` / `micro_cpu.cc`**: The C++ implementation of the `MicroCPU` SimObject, containing the factory methods and the `MicroDump` logic.

## Usage

### Direct Micro-op Injection

You can inject micro-ops directly from your gem5 configuration script into the `Rename` stage of the `MicroCPU`. This bypasses `Fetch` and `Decode`.

```python
from m5.objects.MicroCPU import MicroCPU

# ... system setup ...
system.cpu = MicroCPU()

# ... after m5.instantiate() ...

# Inject instructions
system.cpu.injectAdd(rs1=1, rs2=2, rd=3)  # x3 = x1 + x2
system.cpu.injectSt(rs1=1, rs2=2, offset=0) # Mem[x1] = x2
system.cpu.injectLd(rs1=1, rd=4, offset=0)   # x4 = Mem[x1]

# Simulate
m5.simulate(10000)
```

### MicroDump (Tracing)

The infrastructure allows serializing every executed instruction to a binary trace file for later playback or sensitivity analysis.

```python
# Enable dumping to a specific file
system.cpu.enableDump("trace.bin")

# Instructions renamed during simulation will be dumped automatically
m5.simulate(10000)

# Seal the trace
system.cpu.disableDump()
```

## Internal Architecture

1.  **Injection Queue**: In `src/cpu/o3/rename.hh`, a new `injectedInsts` deque is added.
2.  **Stage Hook**: The `Rename::sortInsts()` method in `rename.cc` was modified to check for injected micro-ops.
3.  **Wrapping**: Injected `StaticInst` objects are wrapped into full `DynInst` objects with proper register indices, sequence numbers, and thread state before being pushed into the backend.
4.  **Dump Hook**: Every instruction passing through `Rename` calls `cpu->dumpInst()`, which performs the binary serialization if enabled.

## Verification & Examples

Several scripts are provided in `util/` for verification:

- **`util/test_gem5_micro.py`**: A general end-to-end test for ALU and memory injection.
- **`util/fuzz_lsq.py`**: A case study stressing the Load/Store Queue using high-density aliasing patterns (Stores followed by overlapping Loads).

To run the verification:
```bash
./build/RISCV/gem5.opt util/test_gem5_micro.py
./build/RISCV/gem5.opt util/fuzz_lsq.py
```

## Trace Binary Format
The `.bin` trace generated by `MicroDump` uses a packed 12-byte fixed-length record:
- **1 byte**: OpCode (from `MuOpCode` enum)
- **8 bytes**: Offset (int64_t)
- **1 byte**: Rd (architectural register index)
- **1 byte**: Rs1 (architectural register index)
- **1 byte**: Rs2 (architectural register index)

This ensures that the exact register state and memory offsets are preserved for playback via `playbackStream(filename)`.
